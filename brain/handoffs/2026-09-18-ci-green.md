# Handoff - CI Verde No Main

## Objetivo

Deixar o workflow `CI` (`.github/workflows/ci.yml`) verde no `main` antes da divulgacao publica do repositorio, sem remover passo, desabilitar ou pular teste.

## O Que Estava Errado

- Todas as execucoes do workflow `CI` falhavam desde a primeira, em 2026-06-12, sempre no job `backend`, passo `./vendor/bin/pest`. O job `frontend` passava.
- Os logs originais do Actions expiraram (HTTP 410). A falha foi reproduzida localmente no commit `11eb071` com o mesmo trace:

```text
TypeError: Pusher\Pusher::__construct(): Argument #1 ($auth_key) must be of type string, null given
  ... BroadcastManager.php:353 -> BroadcastAuthController.php:16
FAILED Tests\Feature\RealtimeAutomationTest > it authorizes only the authenticated user runtime channel
Expected response status code [200] but received 500.
Tests:    1 failed, 38 warnings, 1 passed (147 assertions)
```

- Causa raiz, com duas partes:
  1. `BroadcastAuthController` sempre resolve `Broadcast::connection('reverb')`, mas o ambiente de teste (`backend/phpunit.xml`) nao definia `REVERB_APP_ID/KEY/SECRET`. Sem essas variaveis, o Pusher recebe `null` e o endpoint responde 500.
  2. `routes/channels.php` registra o canal `users.{id}.runtime` apenas no broadcaster default. Nos testes o default e `null`, e o controller consulta outra instancia (`reverb`), onde o canal nao existe. Com as credenciais corrigidas, isso resultava em 403.
- A diferenca de PHP 8.2 (host) para 8.3 (CI) e de Node 24 (host) para 22 (CI) foi refutada como causa: a falha e identica nos dois ambientes.

## O Que Mudou

Commit `f78be75` (`fix(backend): make broadcast auth test run without faking reverb`):

- `backend/phpunit.xml`: `REVERB_APP_ID/KEY/SECRET` com valores ficticios `flowcore-test*`, validos apenas no ambiente de teste.
- `backend/app/Http/Controllers/Api/BroadcastAuthController.php`: registra `users.{id}.runtime` na conexao `reverb` dentro de `__invoke()`, no momento da request. A autorizacao continua a mesma (`(int) $user->id === (int) $id`).

Correcoes descartadas durante a auditoria:

- Um `Event::fake` global de `RuntimeWorkflowUpdated` no `TestCase` foi reprovado porque removia da suite a execucao de `broadcastOn`/`broadcastWith`: um mutante em `broadcastWith()` sobrevivia.
- Registrar o canal em `Broadcast::connection('reverb')` dentro de `routes/channels.php` foi reprovado porque esse arquivo roda em todo boot. Sem `REVERB_APP_KEY`, `php artisan package:discover` quebrava e, com ele, o `composer install` do CI e o build de `docker/backend.Dockerfile`.

Nada mudou em `.github/workflows/ci.yml`, `backend/tests/`, `frontend/`, `docker/`, `render.yaml` ou `routes/channels.php`.

## Evidencia

- CI no GitHub Actions, run `35386407868` no `main` (`f78be75`): `success`. Backend com `Tests: 39 warnings, 1 passed (149 assertions)`; frontend com `Test Suites: 12 passed, 12 total` e `Tests: 30 passed, 30 total`.
- Local: `pint --test` passed; `pest` exit 0 com 40 testes e 0 falhas; lint, typecheck e build do frontend com exit 0.
- Mutante `throw` em `RuntimeWorkflowUpdated::broadcastWith()`: `11 failed`. A cobertura de broadcast continua ativa.
- Checkout sem `.env` e sem `REVERB_*`: `php artisan package:discover`, `php artisan route:list` e `composer dump-autoload` com exit 0.
- Os 39 "warnings" do Pest vem do phpdotenv tentando ler `backend/.env` inexistente; ja existiam antes e nao derrubam o passo.

## Como Verificar

```bash
gh run list --workflow=CI --branch=main --limit=3
cd backend && ./vendor/bin/pint --test && ./vendor/bin/pest
cd frontend && npm run lint && npm test -- --runInBand && npm run typecheck && npm run build
```

Para provar que o boot nao depende do Reverb, rodar em um checkout sem `backend/.env` e sem `REVERB_*` no ambiente:

```bash
cd backend && php artisan package:discover --ansi && php artisan route:list
```
